System Architecture

Lendrail v2 — multi-lender point-of-sale finance orchestration

A clean-room event-sourced monolith: merchants embed a checkout widget, a waterfall router places each application with one of three simulated lenders behind a sealed adapter, and the platform runs the full lifecycle — offers, counter-offers, webhooks, settlement, disputes, and consumer loan servicing — with every state change folded from one append-only journal.

INVARIANT 01
Event-sourced
All state is a pure fold of one append-only JSONL journal. No SQL, no ORM.
INVARIANT 02
Sealed adapters
Lenders see DTOs only — never the store, clock, or HTTP. assess() is pure & replayable.
INVARIANT 03
Router records, never decides
The waterfall sequences legs and freezes a trace; it holds no outcome literal.
INVARIANT 04
Twin reconcilers
Settlement & servicing each pair a deterministic engine with an independent re-derivation.
INVARIANT 05
Virtual clock
Every timer runs on a controllable clock, re-armed from projections on boot.

02

Platform kernel — subsystems

Command handlers dispatch into these services. Each writes journal events; queryable state is the fold. Two subsystems ship an independent verifier that re-derives the engine's claims from the raw journal.

Lenders sealed

  • adapter.ts — DTO-only boundary: assess(input)→assessment
  • policy.ts — one deterministic engine; email-hash credit score, affordability, magic short-circuits
  • registry.ts — priority-ordered lenders (boot config, not journaled)
  • router.ts — waterfall: run leg's lender, probe fallbacks only on decline

Settlement + reconciler

  • engine.ts — clock-triggered per-lender/tenant runs; negative carry-over; SUCCESSFUL→SETTLED; CSV + remittance
  • calendars.ts — per-lender settlement windows
  • reconcile.ts — re-folds the raw journal from scratch; diffs every column (two-derivation gate)

Webhooks

  • notifier / families — map order & dispute status → wire vocabulary; dedupe per checkout
  • outbox.ts — HMAC-SHA256 over canonical JSON; virtual-clock retry ladder 10s→…→12h→FAILED
  • secrets derived, not stored; rotation keeps history so rotated-away keys still verify

Servicing + reconciler

  • service.ts — application.decided→loan.opened; refunds re-split or close
  • schedule.ts — instalment rows via finance-core
  • collection.ts — Direct Debit timer wheel; arrears derived, late-fee ladder
  • hardship.ts — holiday / restructure / reject

Disputes

  • state machine INITIATED → REPRESENTMENT → PRE-ARB → ARBITRATION → CLOSED WON/LOST
  • non-refundable dispute fee; reason-banded response deadline → auto-close LOST
  • CLOSED-LOST emits reversal debiting the lender's next settlement

Identity & tenancy

  • auth/keys · tokens — signing registry; JWT checkout/product/tenant claims (jose)
  • tenants — multi-tenant registration, webhook config, secret rotation
  • admin · lenderops users — RBAC; manual underwriting decisions

Money & offers

  • domain/state.ts — reducer over money + order + journey events
  • pricing/rateCards — priced offers, promos, tenant overrides
  • order status PENDING→SUCCESSFUL→SETTLED (+ counter-offer resurrection edge)

Cross-cutting

  • core/clock — virtual clock drives all timers
  • core/pii · idempotency · rateLimit (token bucket)
  • ais open-banking sim · metrics · audit · reporting · privacy retention & subject-access

The three lenders & the waterfall

All three are the same policy engine parameterized differently. The router runs a leg's own lender and, only if it declines, probes remaining eligible lenders for a counter-offer candidate.

Waterfall (router.ts decideWithWaterfall): the leg's own lender assesses first. On a decline, the router walks remaining lenders in priority order — filtered by ticket band, minus already-used — to the first that acceptsCounterOffers, recording a counterOfferLenderId. It freezes each RoutedInvocation verbatim into a routing.trace event and holds no outcome logic of its own. PRODUCT_LENDERS maps some products (e.g. revolving credit → Fernway) directly, bypassing the waterfall.
